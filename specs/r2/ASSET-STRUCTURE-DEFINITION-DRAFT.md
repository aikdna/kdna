# 判断资产整体结构：本轮定义与现有协议对照

日期：2026-09-23。

范围：接续单议题定义，明确资产名称与简介、内核、议题组织、整体边界、示例和文件信息。Owner 要求先确定完整表达，再谈工程；当前仍为研究和定义阶段，所有产品工程暂停。

本文使用面向人的字段职责名称，不另建公共 wire Schema，不宣称已修改现有协议或获得全部细则的逐项确认。单议题定义继续以同目录 TOPIC-CLASSIFICATION-DEFINITION-DRAFT.md 为本轮底稿；本文只负责资产层，两份文档互相引用，公共协议权威仍在 open/kdna 的当前语义源。

精确候选字段、组合、反例及迁移影响见 [完整定义整理 R1](./README.md)。该包承接本稿职责，不是第三套已发布模型；Owner 最新成题标准也适用于资产内每一个议题。

## 1. 总体结构及信息归属

| 层次 | 保存什么 | Reader 位置 |
|---|---|---|
| 资产基本说明 | 名称、简短简介、身份、语言及必要基本信息 | 页面顶部；详细身份在文件页 |
| 内核 | 共同基础、关键概念、议题组织 | 内核页；必要定义和关系也能从相关议题发现 |
| 议题集合 | 一个或多个完整问题及其判断表达 | 概述左侧问题，右侧显示所选议题 |
| 整体边界 | 整体用途、范围、限制和不承担的事项 | 边界页；影响单题使用时也随该题明确可见 |
| 示例 | 可选的情境、如何采用判断及案例结果 | 示例页，引用实际相关议题 |
| 文件与追溯 | 身份、版本、创作背景、署名角色、来源沿革、修改记录及许可/保护说明 | 文件页；少量基本信息可在顶部呈现 |

这是语义组织，不要求创建六个独立文件或为每个页面复制一份正文。名称、简介和同一条范围/定义/关系各有明确来源；Reader 做不同视图，不能另写第二套含义。

内核、整体边界和资产示例应有明确资产归属。公共读取须能提供作者声明的资产级内容及其引用关系，不能依靠 Reader 遍历全部议题、拼接段落后猜出内核；未被某题引用的真实资产级词条或案例，也不能因此从资产视图消失。读取预算、权限或能力导致只取得部分内容时，必须保留该状态，不能显示成“资产没有”。

当前 Manifest 承担封装与公开元信息，Payload 承担判断语义，Resource 等承接声明的材料资源，公共 Read 提供受支持的读取投影。文件路径、实际大小、当前访问状态由实际读取或宿主提供。新方案须沿用这些职责，不把核心判断塞入 Manifest，也不能让 Reader 私解载荷来补缺失供给。

## 2. 资产名称、简介与身份

| 信息 | 必要性 | 定义 |
|---|---|---|
| 资产名称 | 必需 | 给整个资产命名；可以是名词短语，不要求是问句。该例外不适用于议题名称，议题仍必须是完整问题。 |
| 简短简介 | 本轮建议正式成品必需 | 简洁说明处理什么判断问题、用于什么用途。通常一至两句，不罗列全部议题，也不由 Reader 取正文首段冒充。 |
| 资产身份与版本 | 必需，工具管理 | 稳定身份标识，以及发行版本、判断版本等既有坐标。显示名或文件名不充当身份。 |
| 内容语言 | 应明确 | 单一或多种语言，服务阅读和交换；不是给正文补造语言版本。 |
| 扩展介绍、关键词、封面等 | 可选，按受支持格式 | 有实际用途再提供；当前未支持的内容不能仅凭本稿当作已获格式支持。 |

名称与简介回答“这是什么，能帮助我做什么”；内核的核心问题和共同基础回答“这一整套判断围绕什么建立”。职责不同，同一段相同内容可以引用或复用，不要求维护三份同义介绍。

当前 Manifest 已有 title / summary / description / languages / version / judgment_version 等字段；PublicAssetDeclaration 提供部分公开展示内容。当前 summary 为可选，PublicAssetDeclaration 的 title 结构约束也不能代替正式成品的非空、有意义的标题要求。新必需性要进入共同创作约定，不能声称已经实施。

## 3. 内核固定三部分：共同基础、关键概念、议题组织

内核说明这些议题作为同一判断资产共同存在的基础，不复制概述，不汇总每题的题头和机制卡。

### 3.1 共同基础

| 信息 | 必要性 | 说明 |
|---|---|---|
| 核心问题 | 必需明确 | 整个资产围绕的总问题，采用清楚问句。它不是自动新增的议题，也不必须另造一个总结论。单议题资产可明确复用该题问题。 |
| 共同目标或用途 | 必需明确 | 这些问题共同服务什么判断任务。可以引用已经充分表达用途的资产简介，不强制另填重复段落。 |
| 共同前提 | 存在时必需 | 多题共同采用的事实假设、背景认识或领域前提。没有共同假设时不虚构世界观。 |
| 共同标准与取舍 | 存在时必需 | 跨题共同使用的标准、偏好和优先原则；没有数值权重时不造权重。 |
| 所代表的立场或角色 | 影响理解时必需 | 是个人、组织的判断，还是并置比较多个观点。与创建、整理、发布文件的人区分。各题存在不同主体时明确差异，不能假装大家同意一套共同立场。 |

共同前提、原则和标准需要稳定身份及明确适用位置：它们适用于全部议题还是指定议题，应有可读取的声明。单题使用所必需的共同内容必须能随相关题读取；仅在内核页面出现一段文字不足以建立这种语义关系。共享材料不因在同一文件中就自动成为每题前提。

不强迫所有资产有共同答案。一组用于比较不同观点的议题，可以共享比较问题和用途，保留不同主体的判断及冲突。

### 3.2 关键概念

关键概念用于消除本资产内部的理解歧义。应收录有专门含义、容易混淆、决定分类/选择，或者跨题重复使用且需要统一口径的概念；不复制通用大词典。

一个词条的结构：

| 信息 | 必要性 |
|---|---|
| 概念标识 | 必需，供稳定引用 |
| 词名 | 必需，作者明确声明，不能从正文第一行临时推断 |
| 本资产采用的定义 | 必需，说明在这里是什么意思 |
| 适用位置 | 必需明确，全资产或指定议题；这是本轮语义要求，当前普通 Material 本身没有这一专用字段 |
| 别名、容易混淆的区别、说明性例子 | 按需 |
| 定义来源 | 实际提供时保留，不要求所有术语外部引用 |

同一标准词名不能无声对应两个不同定义。确有不同义项时，应明确区分限定名称和适用位置；当前 PUBLIC-TERM-UNIQUENESS 直接拒绝同资产重复 definition.term，不能借本稿默许违反该合同。未来若改为允许分域同名，须另定作用域与消歧规则，本轮不隐式引入。

术语内容可以随领域不同；词条结构和解释规则固定。它与议题三个标签的封闭选择集职责不同，不要求把所有领域术语列成全世界统一枚举。

### 3.3 议题组织

议题组织至少明确当前有哪些完整问题。多题可以并列，也可有层次或实际关系；不为显得像系统而给每两题连一条箭头。

三种组织信息必须分开：

1. **目录结构**：哪些题并列、哪些题从属于另一题。子题仍有独立完整问题；技术父子层级只表达所属，不自动表达先后推理或范围继承。
2. **判断关系**：某题使用另一题的结果、支持或补充另一题、限定另一题，或与另一题存在冲突。这些关系要明确涉及的议题、方向、作用及必要说明。
3. **建议阅读顺序**：为人提供的进入次序。可以有，也可以没有；列表顺序不自动成为依赖或执行顺序。

用于后续共同语义收口的基本关系职责：

| 关系 | 最低含义 |
|---|---|
| 输入依赖 | 指明谁提供什么、哪题把它作为何种输入，以及该输入是否必要。复用既有 Dependency 职责。 |
| 支持 | 指明某题的什么判断支持另一题的什么主张；不因此把它改造成必需输入。 |
| 补充 | 指明补足哪个方面；不把“相关”当成已经说明作用。 |
| 限定 | 指明限制哪一判断的适用或解释，及相应限制内容。 |
| 冲突或分歧 | 明确分歧点与适用情境。若有作者选定的处理原则则保留；并置比较可以保留分歧，不强迫自动调和。 |

上表是产品职责；R1 COMPOSITION R08已提出完整四套关系元组及读取方向，仍未成为已发布公共枚举。现有通用 Relationship 的 kind / operator / effect / participant.role 使用 TermRef，当前工程核心关系词表未列出这套含义；不能以已有图结构就称跨工具解释已经完整。

替代和撤回继续使用生命周期职责，不另造会与其竞争的关系含义。单纯同属一组用目录即可，不默认存在上述逻辑关系。罕见的新关系不能以任意名称冒充已知语义；须明确其定义、参与方和作用，消费者按支持情况处理，不能猜测。

有反馈关系时，实际循环和停止规则须保留；目录仍不能有环。存在一张关系图不意味着已经支持任意循环求值、联合优化或自动执行。

## 4. 整体边界与议题边界

### 4.1 整体边界回答什么

整体边界负责整份资产的使用外圈：

| 信息 | 必要性 | 内容 |
|---|---|---|
| 整体适用范围 | 必需 | 面向什么对象、任务、情境；有时间/地区/数据/人群限定时明确。 |
| 整体不适用事项 | 存在时必需 | 本资产明确不回答或不承担的范围。 |
| 整体使用前提 | 存在时必需 | 使用各题都需要满足的前提。只作用一题的条件归该题。 |
| 整体限制与误用提醒 | 存在时必需 | 会影响理解和采用的重要限制。 |
| 整体角色与责任边界 | 存在时必需 | 承担什么判断角色、不承担什么职责；不是账户访问授权。 |

内核中的核心问题说明共同任务；范围与限制在边界层维护。内核和顶部可呈现相关引用，不另外维护一套竞争的范围定义。

### 4.2 两级边界怎样协作

- 明确声明作用于全资产的限制，对各题共同适用；单题再声明其局部范围、限制、例外和误用提醒。
- 单题可以进一步缩小或补充限制，不能默默扩大整体范围。确需全局限制的例外，必须在整体声明中明确允许该例外并指明适用题与条件，不能由局部文字偷偷覆盖。
- 如果一条限制实际只作用部分议题，应明确其归属，不能写成不加限定的全局限制。
- 全资产限制与本题限制冲突时，创作需要澄清；工具能确定的结构冲突可以拒绝，不能声称工具自动理解并发现所有自然语言冲突。
- 缺少额外限制声明不等于无限适用。明确没有额外限制、尚未提供和无法读取保持区分。
- 父子议题不会因为目录包含就自动继承对方边界。这与明确全资产适用的共同限制不同。

这些是本轮拟明确的作用域与一致性要求。当前协议有两级字段及父子不继承规则，不能据此声称全资产与局部组合、例外和冲突处理已完整落地。

单题页面应让人能发现有效的整体限制和本题新增限制，并标清来源，避免在两处维护两份相同正文。边界页的主体是整体边界，可提供局部差异入口，不堆积所有议题的全部长文。

## 5. 示例：可没有，有就结构清楚

没有示例的资产仍可完整。一个示例可以涉及一题或多题，不必为每个议题生成一个，也不能把案例结果自动提升为普遍判断。

一个示例至少包含：

| 信息 | 必要性 | 说明 |
|---|---|---|
| 标识和名称 | 有示例时必需 | 用于选择、引用和追溯，不冒充新议题 |
| 示例性质 | 有示例时必需 | 说明性案例或实际案例；实际案例须有实际记录依据，不把编写示意说成实际发生 |
| 情境和输入 | 有示例时必需 | 面对什么情况、已有何种材料 |
| 采用的议题与版本 | 有示例时必需 | 指向具体判断身份；随同本资产时可由容器身份及议题 ID 绑定，不强迫重复抄版本 |
| 应用说明 | 有示例时必需 | 采用了哪些标准/条件，如何形成案例中的判断；简单例子可很短，不强制完整执行日志 |
| 案例结果 | 有示例时必需明确 | 展示结果；若案例有意演示资料不足或不适用，则明确该处理，不编造答案 |
| 差异、反例、复盘、来源及相关附件 | 实际需要时 | 保留重要信息和授权披露范围 |

建议参考答案、作者的历史选择和真实运行观察的身份要明确。案例“没有采用该规则”或“因为范围不符而停止”也能帮助理解边界。

案例所用的旧版本应保持原引用；资产修订后不能悄悄把旧案例改成对新版本的证明。完整私人输入不要求打包，必要可披露语义仍须完整。当前 Material.kind=example 可保存材料，但没有上述完整案例专用结构，具体如何复用材料/资源/关系或新增共同定义尚待合同设计。

## 6. 文件页：身份、来历、变更、使用说明

文件页以人能理解的追溯为主，详细技术诊断另有可发现的展开位置。

| 内容组 | 信息 | 必需性与界限 |
|---|---|---|
| 文件身份 | 名称、资产标识、发行版本、判断版本、创建/更新时刻、语言 | 当前 Manifest 已有主要字段；名称复用顶部来源。文件系统修改时间不能替代作者声明的更新时间。 |
| 创作说明 | 创作目的或背景、实际提供的资料来源、采用过程的必要说明 | 需要解释来历时提供；与内核的判断共同前提区分，不强制附全部创作日志。 |
| 署名与角色 | 作者/所代表主体、整理者、维护者、发布者等实际声明角色 | 仅声明实际存在角色，不推导“创建文件的人就是每题观点拥有者”，不强制公开真实姓名，不造匿名占位身份。 |
| 版本沿革 | 当前版本从何而来、来源资产与版本、有哪些明确的演变关系 | 按实际记录保留；现有 lineage 主要记录来源版本，不是完整修订日志。 |
| 修改记录 | 哪一修订、何时、修改什么、涉及哪些议题/概念/范围，前一版本引用，实际记录的修改者 | 有修订时需要可理解的变更记录。记录身份、时间、变化和前版关系，不能自动编造失落历史。历史覆盖完整或有限必须明确。 |
| 使用说明 | 已声明许可、分享/获取方式、保护方式，及本次实际读取状态 | 权利声明、技术加密、当前授权/解锁状态分别显示。没有许可声明不等于任何用途均已允许。 |
| 技术详情 | 格式和协议版本、大小、校验标识、兼容诊断等实际供给 | 按需展开，默认不淹没创作背景和修改说明。当前会话或宿主状态不写成永久资产事实。 |

发行版本和判断版本使用既有身份坐标，具体变更判定须服从当前公共版本合同；本稿不把旧文档中的版本样例当作当前规则。资产源流、同一资产的修订历史、单题的替代/撤回各有职责，应能相互引用，不能用一个 version 字符串冒充三种追溯均已具备。

“记录充分”不要求当前文件嵌入全部历史版本的字节。历史可以有明确引用和覆盖范围；若前版或材料不可取得，应如实显示能追溯到哪里。签名、哈希和创建者字段也不能替代实际变更说明。

授权、解密的真实执行由已有工具与访问合同负责；本轮定义只明确保存和呈现的信息，不增加账号系统、商业操作或公开发布范围。

## 8. 全结构收口条件

每项结构都须有：明确职责、类型和数量、必需性、没有与未提供的区分、身份和引用、作用范围、与其他声明的组合规则、公共读出与人类显示位置。字段只是可存在、正文只是可装入，不能算完整定义。

下一步仍在定义范围内，先完成以下一致性核对：

1. 名称/简介/核心问题/范围职责不重叠，不维护互相漂移的副本。
2. 每题共同依赖的前提、概念和全局限制能随该题取得；多个独立议题也不被强造依赖。
3. 关系端点、输入角色、概念词名及作用范围可解释；目录与阅读顺序不冒充推理关系。
4. 全局与局部范围/例外的作用清楚，冲突不被静默覆盖。
5. 没有概念、没有示例、只有一题、很多题、多主体不同观点、局部例外、旧版本案例等均有正确表示。
6. 文件追溯保留真实身份、来源和变更，声明与当前访问状态分开；公共读取能够提供必要信息，Reader 不靠私解载荷补洞。
7. 既有语义逐项承接，旧字段及已表达内容不因重构丢失。新必需项进入共同合同和创建检查后，才重新评估协议与工具交付状态。

这不是“过去所有封装、加密和读取成果无效”的结论。严重失误在于：尚未证明完整的判断表达需求已经被共同合同覆盖，就把技术局部通过扩大成了上游整体完成，并推动了下游。此次以具体内容职责和可核查映射收口，不能再用字段存在、测试数量或 Reader 能打开代替。
