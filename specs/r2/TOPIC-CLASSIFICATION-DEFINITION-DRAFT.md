## 0. 本轮面向读者的名称修订

用户指出“已形成结论 / 结论形成规则”难以直接理解，并要求其他维度一并纠正。三个已确认的职责保持为判断形态、回答类型、形成方式；下面统一其类别名称和日常含义。

| 维度 | 用日常话解释 | 示例 |
|---|---|---|
| 判断形态 | 给出答案，还是给出得到答案的办法？ | 结论 / 规则 |
| 回答类型 | 这份判断回答的是哪类问题？ | 偏好、评价、诊断、选择等 |
| 形成方式 | 作者怎样作出这个判断？ | 感受、经验、对照、权衡等 |

名称尽量简短，但含义保留在明确的类别定义中。这些是共同分类的人类名称，未来创作、公开读取、Reader 和 Agent 应同义消费，不是由 Reader 临时改写。“答案 / 办法”用于解释第一维，不另建与“结论 / 规则”竞争的第二套名称。

区分三个维度的最小例子：同样都给结论，可以是在表达偏好，也可以是在作出评价；同样都作评价，可以凭感受、凭经验，也可以对照明确标准。回答类型不自动决定形成方式。

本轮把“偏好”从宽泛的立场类明确分出，并补入“经验”方法，避免将作者表达的喜恶与经验硬塞进复杂推理术语。它们是定义稿中的本轮修订，不是已实施的协议变更。其余类别以现有工作编号保留追溯；编号不是显示文案或公共协议枚举。

## 1. 三个标签的共同规则（用户已确认三维必选）

- 一个议题以作者完整问题为名称；分类针对该议题在资产中保存的判断表达，不根据问句猜测。
- 三个维度固定为：判断形态、回答类型、形成方式。每题每维必须且只能选择一个已有类别，不得省略、多选或填写未定义值。不同议题可以同类，不承担唯一标识作用。
- 任一议题缺少任一分类、填写空值/未定义值或多值时，创作工具必须报出议题和缺失项，并阻止生成可交付资产；不得默认选择规则、其他、文字回答等替代真实选择。创作材料可保留在会话草稿中，但不能产出不满足要求的正式 .kdna。
- 复合类型是一个有明确组成的类型，不能静默挑一个子类；其他类型是现有列举之外的已说明类型，不等于遗漏。认识上的不确定或记录不完整，不自动成为一种判断方法。
- 判断资产表达并保存作者的判断、品味、标准，以及实际表达的依据、取舍和形成规则。分类服务于理解这些内容；机制组件展开这些内容之间的关系。
- 分类是共同语义约定。作者/创作 Agent 明确赋值并核对内容，公共工具验证供给和一致性，Reader 读取并呈现，不重新猜分类。
- 源码字段如何承接这些含义另行设计。本稿中文标签和下文工作编号不是已发布 wire 枚举。

## 2. 判断形态：结论 / 规则

| 工作编号 | 标签 | 定义 |
|---|---|---|
| F01 | 结论 | 直接给出作者对这个问题的答案。 |
| F02 | 规则 | 给出得到答案的办法，包括标准、条件、方法或流程。 |

此维不设“其他”。规则里的示例结论不改变规则身份；结论的论证过程也不自动把它变成形成规则。作者须明确当前判断表达的身份。没有判断表达的裸问题仍是待创作内容，不能靠填标签冒充完成的判断资产。

## 3. 回答类型：这份判断回答什么

依据是对问题承诺提供什么意义的回答，不是文字/数字/列表等编码形状。规则型议题按规则承诺产生的回答归类；结论型议题按已保存的回答归类。

| 工作编号 | 标签 | 定义与边界 |
|---|---|---|
| A01 | 判定 | 判定可由事实或证据核对的命题是否成立、受支持、被反驳或暂不可判；专门的类别、程度、状态等优先采用下列具体类型。 |
| A02 | 分类 | 判定对象属于哪类、不属于哪类；分类依据与类别定义须存在。 |
| A03 | 评价 | 根据评价标准判断好坏、水平、高低或风险程度；与有单位的数量估计区分。 |
| A04 | 状态 | 判断对象在某一时点/阶段处于何种状态，如运行、异常、待确认；不因它也可表示成类别就自动改成 A02。 |
| A05 | 诊断 | 回答现象由哪些原因或机制解释，包含多个候选原因及证据不足。 |
| A06 | 估计 | 回答数量、概率、范围或区间；编码为数字并不自动归此类，例如数字编码的等级仍是 A03。 |
| A07 | 预测 | 回答未来可能的方向、状态、变化或情景；若核心交付是预测结论，用此类，不能只因输出一个数就归 A06。 |
| A08 | 适用 | 回答规定、义务、许可、禁止或例外在当前条件下是否适用；与一般事实真假判定区分。 |
| A09 | 排序 | 回答对象间的优先、偏好或等级顺序；结果是关系/次序，而不只是最终选一个。 |
| A10 | 选择 | 回答应选择什么方案、行动或是否采取行动；不把用于选择的排序依据也自动计为另一回答。 |
| A11 | 调整 | 围绕已有行动或系统，回答增强、减弱、保持、等待、停止或修订什么；区别于首次方案选择。 |
| A12 | 解释 | 回答文字、行为、现象在语境中是什么意思；解释致因则用 A05，兼具两个独立回答则用 A15。 |
| A13 | 立场 | 回答赞成什么、反对什么、坚持什么价值或原则；个人喜恶用 A17，明确的评价、排序或行动选择采用相应具体类别。 |
| A17 | 偏好 | 回答个人喜欢什么、不喜欢什么、倾向什么；涉及几个对象仍可属于同一偏好类型，不自动成为综合回答。若专门交付明确先后次序，则采用排序。 |
| A14 | 指导 | 回答实现目标或作出判断应怎样做、按什么程序/步骤处理；只有执行步骤且没有任何判断内容的纯操作说明，不能仅靠此标签宣称成为判断资产。 |
| A15 | 综合 | 同一问题确实要求两个或以上不可互相替代的回答职责；逐一声明常用类别或 A16 的组成及关系。中间推理、证据和例子不算第二个回答。 |
| A16 | 其他 | 回答意义已经明确，但无法忠实归入以上类型；必须附具体名称、定义及不能归入既有类别的理由。标签仍是单选的“其他”，具体名称与定义写在说明中，不成为 Agent 自创的新类别。不能填空白解释。 |

归类优先规则：先看题头判断及实际/承诺输出的职责；多个现有类重叠时采用最具体的一类，例如当前运行状态归 A04、未来状态归 A07、规范许可归 A08。若不同职责各自构成不可省略的回答，用 A15；若只是同一回答的手段、理由或表现形式，不制造复合类型；确实没有合适类别才用 A16。仍有歧义时须回到作者声明并独立核对，不能把任意多标签隐藏成一个默认值。

“培训”属于用途/情境，不与诊断等并列：培训中的能力判断可属程度评价，薄弱原因属原因诊断，练习步骤属操作指引。这不预设用户口述“培训”是否为其它词的转写。

结果为“证据不足/暂缓判断”不自动变成其他回答：它仍可属于事实判定、原因诊断等已明确的问题类型，认识状态另外保留。

## 4. 形成方式：作者怎样作出这个判断

形成方式说明作者基于什么方式作出这份判断：可以是观察、推理、规则，也可以是明确表达的主观感受、经验或价值取舍。机制组件展开其中实际表达的依据及关系。已有结论和形成规则都可采用适合的方法；不能按形态硬排除方法。下表是待整理的角色示意，不是每题必须填满的卡片模板；只有实际采用的角色才成为组件。

| 工作编号 | 标签 | 决定性特征 | 可能承担机制作用的组件 |
|---|---|---|---|
| M01 | 观察 | 通过明确观察、感知或测量及判定口径获得判断 | 观察/测量依据；判定口径；误差与限制 |
| M02 | 识别 | 将对象特征与已定义模式匹配 | 识别特征；候选模式；区分标准 |
| M03 | 对照 | 按评价标准与综合规则形成评价 | 评价标准；证据对应；综合/分级规则 |
| M04 | 权衡 | 对候选项作比较，处理目标间的取舍 | 比较对象；比较维度；取舍原则 |
| M05 | 推理 | 从明示前提与规则推导可接受结论 | 前提；适用规则；推导关系/例外 |
| M06 | 排除 | 用必要条件或否决条件排除不符合者 | 候选集合；排除条件；保留依据 |
| M07 | 因果分析 | 在候选原因间建立和检验因果解释 | 候选原因；因果证据；区分检验 |
| M08 | 计算 | 用变量、模型或计算关系获得结果 | 输入变量；模型/假设；计算关系；误差/边界 |
| M09 | 推演 | 从初始条件和变化假设推演可能演变 | 初始条件；情景假设；演变关系；转向信号 |
| M10 | 证据分析 | 比较支持和反对理由，说明主张成立程度 | 待支持主张；支持依据；反证/异议；证据权衡 |
| M11 | 解读 | 结合语境与对象建立可核对的意义解释 | 原文/对象；语境；解释关系；替代解释 |
| M12 | 反馈调整 | 根据目标与当前反馈反复修正判断或行动 | 目标/基准；反馈；调整规则；停止界限 |
| M13 | 类比 | 根据参照案例及相似/差异关系迁移判断 | 参照案例；相似与差异；迁移限制 |
| M14 | 感受 | 判断直接基于主体明确表达的喜恶、感受或偏好 | 真实声明的感受与偏好，以及实际提供的解释 |
| M18 | 经验 | 作者明确依据过去实际积累的经验或惯常认识作出判断，不要求一定展开为某个具体案例的类比 | 已表达的经验要点、适用情形与例外；没有提供的经历不补造 |
| M15 | 综合 | 两种以上具有独立作用的方法协同，不能忠实归为某一单一方法 | 明示方法组成及先后、并行、约束或反馈关系；组件不重复计算 |
| M16 | 其他 | 已说明怎样判断，但不属于上述方法 | 必须具名、解释方法和实际组件；不得只有“其他”二字 |

判别以实际采用的决定性关系为准：使用数字不自动是计算建模，使用证据不自动是证据论证，提到过去不自动是案例类比，使用 if 不自动是规则推导。一个方法内部必要的观察/比较等步骤不是自动升级为复合方法的理由；只有多个方法各自承担独立、不可省略的判断作用时才使用 M15。

方法内部组件可以不同；相同方法不意味着相同组件数。同一组件角色可以包含许多条目。例如十条评价标准通常是一份“评价标准”组件，不是十张机制卡。

原 M17 已撤回。它把记录是否完整混入了判断方法的分类。一个人明确说“我喜欢苹果、讨厌香蕉”，已经表达个人偏好，不能因为未解释喜恶的心理成因就归为未知方法，也不能因为提到两个对象就归为复合回答。机制组件呈现作者实际表达的依据和组织方式；不能为凑组件重复抄写结论或补造理由。

## 5. 机制组件数量与阅读上限

这里决定的是内容组织和阅读负荷，不把数字 5 或 7 宣称为普遍认知定律。

- 组件是承担明确逻辑职责的内容单元，不是每一条证据、字段、评价维度或流程步骤都单独生成一张卡。
- 正常设计目标：每题 1–5 个主要机制组件；简单判断可以只有 1 个。6–7 个可以接受，不凑固定三个/四个，不为整齐补空卡。
- Reader 默认最多展示 5 个组件标题，正文默认折叠。共有 6–7 个时，明确显示总数与“展开其余 N 项”；展开后可查看全部。
- 真实组件超过 7 个时，触发创作组织复核，而非直接判资产非法：如果实际存在共同逻辑，可以由作者明确组织成较少的机制分组，保留全部子组件及关系；Reader 不自行编造分组。
- 超过 7 个、且没有作者明确分组时，完整保留组件，按每页 5 项浏览，始终显示总数和翻页入口；不得静默只取前五/前七，不要求用户另找“判断全文”才能发现剩余机制。
- 不给协议底层真实组件数设置 7 的硬上限。一个问题可能复杂；显示负荷与资产语义容量不能混为一谈。已有预算等技术限制另按公共合同，不由本稿宣布无限资源支持。
- 判断形态/回答类型/形成方式不是三个机制组件。方法的职责定义约束必要角色，但不同议题采用的实例数量由真实内容决定。
- 机制区说明如何判断；下方条件与结果说明什么情境对应什么处理。相关内容保持引用和职责，不为填三个板块重复抄写或丢掉条件。

## 6. 示例（仅说明定义，不是对正式 095 的修订）

| 完整问题 | 假设实际保存的内容 | 三个标签 | 合理的组件示例 |
|---|---|---|---|
| 我喜欢哪些水果，不喜欢哪些？ | 作者明确说喜欢苹果、讨厌香蕉，未声称有进一步理由 | 结论 / 偏好 / 感受 | 如实保存个人偏好；不编造口感、经历或论证，不因两个对象而判为复合，不凑多张卡。 |
| 这个苹果是甜还是酸？ | 已有明确品尝记录，并据口味标准作出甜/酸/兼有判断 | 结论 / 分类 / 观察 | 品尝记录；甜酸判定标准；样品与观察限制。实际足够时可更少，不凭空生成记录。 |
| 什么样才算一个好标题？ | 保存按准确、清晰、吸引力及底线评价标题的方法 | 规则 / 评价 / 对照 | 评价标准；事实对应；底线条件；综合规则。 |
| 这组数据应该用什么图形展示？ | 保存对候选图形按任务和数据条件作取舍的规则 | 规则 / 选择 / 权衡 | 读者任务；数据条件；候选比较；取舍原则。 |

同一个问句若保存的是不同作者的另一种判断表达或方法，分类可以不同。以上分类不能仅凭问句直接赋予。

## 7. 归类与验收的实际规则

1. 明确问题及该题承诺回答什么，再指定两种形态之一。
2. 根据实际/承诺输出选择回答类型；先具体、再复合、最后有定义的其他。
3. 根据明示判断逻辑选择形成方式，并对应实际机制角色、内容与关系；不从前两个标签自动推断方法。
4. 核对三个标签与题头、机制、条件结果是否一致。没有资料支持的内容不能靠 AI 填补后当作原作者声明。
5. 其他类型附明确名称和定义；漏填、解析失败、权限不足、未支持或形成细节未记录等状态，不变成判断方法类别。明确的偏好、感受和经验按其实际内容分类。
6. 用跨领域同方法、同问题不同方法、复合回答、偏好主张、无法还原的既有结论、新方法等反例检验；一份 095 或格式测试通过不证明全分类完成。
7. 三维的可接受值和含义必须进入共同语义约定；具体编码、版本兼容、生成器与工具支持另行工作，不用 Reader 私有映射代替。新增分类的解释必须让独立消费者可理解；“其他”不能被误当成其所有子类型互相等价。

## 9. 三维单选的创建约束（本轮 Owner 明确要求）

当前固定选择集为本文件表中的工作定义：

- 判断形态（2）：结论、规则。
- 回答类型（17）：判定、分类、评价、状态、诊断、估计、预测、适用、排序、选择、调整、解释、立场、偏好、指导、综合、其他。
- 形成方式（17）：观察、识别、对照、权衡、推理、排除、因果分析、计算、推演、证据分析、解读、反馈调整、类比、感受、经验、综合、其他。

一个议题必有三个明确单选结果。创作 Agent 可以依据材料建议选择，但写入时必须选择已定义类别；Reader 只读，不参与分类。类别变更须改共同定义，不能由一次创作临时添加。

“综合”仍是顶层的一个单选值，组成在对应正文结构中明确，不能把顶层单选字段偷偷变成数组。“其他”也是已定义的一个单选值，其说明不得被当成新枚举或未定义的模板权限。工具不得在缺选择时自动填“其他”。

下列情形阻止生成资产：任意一维缺失/空白/多选/未知值；综合未给出真实组成；其他未给出具体说明；形成方式已选但对应必需机制角色缺失或没有实际内容。报错应指出具体议题与具体项，保留创作输入，不把拒绝生成等同于丢弃用户材料。对正文是否忠实于作者表达的核对不能仅靠字段存在代替；也不在此重新评价作者判断的对错。

## 10. 形成方式 → 机制组件映射（本轮具体方案，尚未实施）

### 10.1 职责与映射规则

- 形成方式决定组件的语义职责与必需/可选项。模板在共同定义中给出，Creator 据此收集和保存内容，公共读取保留身份与关系，Reader 据此显示。
- 判断形态决定内容表达：结论记录作者实际表达的依据和采用方式；规则记录需要什么输入、按什么标准或关系处理。不能要求规则必须已有现场观察，也不能替既有结论编造实际操作记录。
- 回答类型决定方法需要服务哪一种输出，如评价、排序或选择；它不自动决定用哪种方法，也不单独固定组件个数。
- 组件按作用划分，不按句子、证据条数或标准条数生成。一组十条标准通常保存在一个“判断标准”组件内。
- 固定语义职责不要求固定领域正文。作者可为组件提供简洁的内容标题，如“标题准确性与清晰度”，但不能据此改变其“判断标准”角色；Reader 不能从自定义标题反推角色。
- 必需角色都有实际内容，才允许生成；可选角色只有实际提供了内容才保存和显示。不能保存空组件占位，也不能为填模板编造材料。

### 10.2 映射表

下表确定基本组件职责。普通方式的必需角色各占一个组件，内部可容纳多条内容；可选角色按实际内容采用。角色名称是本轮方案，不是已存在的公共组件类型。表中的基本组件总数通常为 1–5，超过时沿用完整保留与阅读分组规则。

| 形成方式 | 必需组件 | 可选组件 | 基本组件数 |
|---|---|---|---|
| 感受 | 个人感受 | 体验说明、偏好变化 | 1–3 |
| 经验 | 经验要点 | 参考经历、适用情形、例外情况 | 1–4 |
| 观察 | 观察依据 | 判定口径、观察限制 | 1–3 |
| 识别 | 识别特征、类别定义、匹配办法 | 易混淆情况 | 3–4 |
| 对照 | 判断标准、对照办法、归结办法 | 底线要求、例外情况 | 3–5 |
| 权衡 | 候选方案、比较因素、取舍原则 | 不可兼得之处、优先变化 | 3–5 |
| 推理 | 判断前提、推导关系 | 关键假设、例外情况 | 2–4 |
| 排除 | 候选范围、排除条件、保留办法 | 特殊情况处理 | 3–4 |
| 因果分析 | 待解释现象、原因关系 | 候选原因、区分依据、反向情况 | 2–5 |

| 证据分析 | 所用材料、材料与判断的联系 | 反向材料、材料取舍 | 2–4 |
| 解读 | 解读对象、解释关系 | 相关语境、理解线索、替代解读 | 2–5 |
| 反馈调整 | 调整目标、反馈信号、调整办法 | 停止条件、冲突处理 | 3–5 |
| 类比 | 参照对象、对应关系、借用办法 | 关键差异、不可迁移之处 | 3–5 |
| 综合 | 各组成方法的必需组件、方法间的组合关系 | 各组成方法中实际需要的可选组件 | 按真实组成，允许有明确关系的分组 |
| 其他 | 方法说明、判断依据、作用关系 | 补充说明、适用限制 | 3–5 |

### 10.3 必需内容怎样定义，避免只填标题

- **感受 → 个人感受**：保存作者明确表达的喜恶、感觉或倾向。“喜欢苹果、讨厌香蕉”本身可以满足，不要求追加喜恶的原因。可以引用已保存的同一份表达，不为了组件再生成一段理由。
- **经验 → 经验要点**：保存作者明确表达的经验认识；未讲具体经历时不编经历。若规则型，经验要点须说明据此怎样判断。
- **观察 → 观察依据**：结论型写实际表达的观察；规则型写需要观察什么及怎样用观察结果回答问题。规则型不能只有“观察”二字或虚构一份现场数据。复杂判定口径可在可选角色展开，关键含义仍须存在。
- **对照 → 判断标准 / 对照办法 / 归结办法**：分别说明看哪些标准、如何把对象与标准对应、如何由对照得到本题回答。多个标准没有数字权重时不能强造权重；可以由明确的定性原则归结。
- **权衡 → 候选方案 / 比较因素 / 取舍原则**：分别说明在什么范围选、比较什么、冲突时怎么取舍。规则型可以声明候选范围和进入条件，不要求事先列出未来所有方案。
- **计算、推演等**：规则写输入定义和关系，结论写作者实际采用并表达的输入和关系；不得把预期执行写成已发生事实。
- **综合**：顶层方法只选择“综合”；明确至少两种实际采用且有独立作用的基本方法及组合关系；同一种方法使用两次不算综合。基础方法单元不再选综合，但有限多层组合由R1 Plan/实例/端口表达；“其他”若参与，仍用其既定模板。不强行重复同一真实组件，明确引用、所属作用和关系。
- **其他**：顶层方法仍选择“其他”。以固定三个职责说明特殊方法，不允许自由增加新的顶层类别或未定义组件角色。

可选的意思是不要求每份资产都具有该内容；如果作者已经表达且会影响理解或应用，必须保留在对应组件或已有条件/边界位置，不能因为它在模板中是“可选”就删掉。组件和条件区之间可引用同一声明，不重复造两份不一致文本。

### 10.4 创建与消费的对应

1. 创作侧选定三个类别后，按形成方式取得模板；必需角色明确提示，正文由作者/Agent 根据材料填写。
2. 保存前核对选择合法、必需组件齐全、内容存在、角色属于模板、引用属于本议题或有明确可用关系；缺一项报出议题及组件，阻止生成。
3. Agent 不能用错误方法模板凑内容，例如选择“权衡”却只提供“个人感受”；也不能给必需标题填无关正文冒充完成。结构问题可由工具确定拒绝，内容与作者表达是否一致另需实质核对，不声称 Schema 可自动理解所有正文。
4. Reader 按声明角色和作者内容显示；默认折叠、不自动补组件、不猜方法、不把一个组件的多条内容擅自变成多张卡。
5. 单个例子：标题评价选择“规则 / 评价 / 对照”，必需提供判断标准、对照办法、归结办法。只写“准确、清楚、有吸引力”提供了标准，尚未交代怎样对照及归结，不能只靠三个标签就当作规则已经完整。

本节是当前映射提案，尚未执行产品修改。用户已确认的三维必选要求不会因映射还在讨论而退回为可选。


## 11. 题头核心判断与完整展开（本轮具体方案，尚未实施）

### 11.1 用户的新要求与已有确认

用户明确表示标签问题在定义上已经解决，要求每个议题的题头能让人约十秒把握核心；提出中文二三十字或三四十字的简洁目标，同时担心“短结论 + 长结论”变成两套内容。此前 Owner 已明确否定题头的“阅读完整判断原文”入口、问题充当右侧结论、首段截取和机械预览；这些约束继续有效。

本节给出结构与创作方案，用户尚未确认具体字数规则和表达承载方式。标签定义上的收口不表示当前协议、工具和 Reader 已修好。工程保持暂停。

### 11.2 一份判断，核心句与各项展开分别承担职责

每个议题有一个由作者/创作 Agent 明确写定的“核心判断”表达：

- 选择“结论”：用简洁话直接说明作者的答案、选择、偏好或立场。
- 选择“规则”：用简洁话说明决定答案的核心标准、原则或办法，而不是只写第一步。
- 题头完整显示这句话及三个标签。它不是第二个议题名称、导航短标题、文章标题、内容简介、自动摘要或原文预览。
- 机制组件展开按什么感受、经验、标准、关系或步骤作出判断。
- 条件与结果保留不同情形的具体处理、分支和详细结果；完整结果包含长列表、表格等时，按其真实结构完整保留。
- 必要的边界、定义、依赖及引用仍属于同一议题的完整表达，按其真实职责保留。

完整判断由这些内容共同构成。不存在一篇独立的“短结论”和另一篇独立的“长结论”分别维护。题头核心句不是完整可执行规则的替代物；Agent 实际采用必须取得相关机制、条件、结果和必要依赖，不能只取题头。Reader 中也不能将关键内容移入无人可发现的来源附件。

核心句与展开之间仍然可能发生语义不一致；分层结构不自动消除这一风险。必须在同一议题、同一修订中对照维护，不能仅因拥有共同 ID 就宣称一致。

### 11.3 简洁要求怎样落地

- **共同语义要求**：每题存在非空、明确可读取的核心判断，并能对应左侧完整问题；不能由 Reader 自行挑首段、截字数或生成一句替代作者表达。
- **中文创作目标**：通常一至两句、20–40 字左右；需要关键限定时允许更长。超过约 60 字触发编辑检查，优先重写和整理职责，而非自动截断。
- **不设 40 字的永久协议硬上限**：字数属于语言相关的创作与阅读约束；不能为了过字数门槛丢掉会改变核心判断的限定。其它语言另定等效可读标准，不按编码字节机械套中文数字。
- **题头必须保留的限定**：删去后会把局部主张变成全局主张、把有条件选择变成无条件选择、把一个分支误当总体回答的内容，应留在核心句或其紧邻且默认可见的必要限定内。不能靠远处折叠内容事后纠正题头的误导。
- **可展开的内容**：具体标准条目、理由、例子、比较过程、执行细节和分支说明，按真实作用进入相应组件及条件结果区；不能任意截断搬走。
- **阅读验证**：约十秒的目标以读者能复述“该题的核心回答或判断原则”为准，字符数只用于提醒；不能声称符合字数就已经通过人工可理解性验收。

若必要限定使题头过长，应继续编辑其表达和职责组织；在忠实而简洁的版本形成前保留为创作中的待完善项，不能把删掉限定的短句交付为完成品。简单判断不必填满字数，短于二十字完全允许。

### 11.4 创作和修订流程

1. 从真实材料确定问题、三个分类、核心回答及必要展开。
2. 写定核心句，再逐一核对它是否真实概括本题主张，而不是第一步、介绍语或口号；也可先整理展开再写核心句，顺序不强制。
3. 将每条细则、例外和材料安排到明确位置；出现无法归位的实质内容时先报告表达缺口，不能把它删掉或全部塞到附件中。
4. 检查核心句、机制、条件和结果是否相符，尤其是核心句里省略的条件会不会改变人的理解。
5. 以同一议题修订保存这些内容。修改会改变主张的细则或条件时，同时复核核心句；改变核心句时反向复核展开。不得把核心句作为与作者正文分离的 Reader 私有缓存。
6. 公共读取提供明确核心表达及必要展开；Reader 原样呈现，经允许的排版改善可读性，不在打开文件时现场摘要。

这些检查关注忠实表达和内部一致性，不替作者选择价值、偏好或结论。

| 议题与形态 | 题头核心判断示例 | 展开内容去向 |

### 11.6 与现有协议的差距及历史反例

本轮只读核对当前 public-semantic-source.json：Judgment 通过 form 区分结论/规则，规则的 formation_rule.statement 为不限定简洁职责的 NonEmptyText，结论通过 Result 的类型化 value 保存；尚不能从这些字段存在推出“每题统一、明确、可直接读取的题头核心表达”已经交付。

C05 曾把五句导语加在长 statement 开头，工作包明确允许“原文预览与完整阅读入口”。那只是同一长字符串的段落安排，Reader 仍按多段取首段并增加全文入口，没有建立本节提出的表达职责。此次方案不能复用该行为称为完成。

后续具体复用或调整哪个公共字段，须联合现有结论结果、规则、组件及条件结构形成同版合同和迁移方案；本节不私自新增 wire 字段、不把一个 UI 摘要属性变成规范。旧长文必须逐项保留语义和归属，不能用“拆入组件”之名消除限定或变成两个独立版本。用户未授权恢复工程，本次仅记定义与分析。

## 12. 条件与结果：本轮补充定义

### 12.1 职责及与其他部分的区别

“条件与结果”回答：**在什么情况下，本题给出什么答案或处理；哪些具体结果需要展开。** 它是一个按内容需要出现的区域，不是每题都必须填满的第三张卡，也不是全文收纳区。

四种内容分别保留其职责：

| 内容 | 回答的问题 | 例子 |
|---|---|---|
| 核心判断 | 本题的主张或核心办法是什么？ | 按读者任务和数据条件选图。 |
| 判断机制 | 按什么依据、标准或关系判断？ | 比较阅读任务、数据条件和各候选图形的得失。 |
| 适用范围与边界 | 本题管什么、不管什么？ | 适用于说明性数据呈现，不讨论装饰性插画。 |
| 条件与结果 | 某种情况对应什么具体答案或处理？ | 若主要任务是精确查值，则以数值表为主。 |

以上是说明性例子，不是正式 095 原文或内容修订。条件改变答案、范围限定适用领域，二者可以有关联，但不能互相代替。某项条件如果属于机制内部步骤，则留在其步骤及关系中；不为第三块另抄一份。多个区域需要同一声明时保持同一内容身份及明确引用。

### 12.2 什么时候显示，什么时候没有

| 实际内容 | 呈现方式 |
|---|---|
| 简单结论，题头已完整表达，作者没有额外条件或详细结果 | 不显示空的条件结果区。例如个人水果偏好不必伪造分支。 |
| 规则是统一标准、顺序流程或公式，没有按情况改变处理 | 完整办法在机制中表达；不强造 if/then。规则不等于必有分支。 |
| 只有一个必要适用条件，没有多个备选处理 | 明确显示“适用条件 → 本题判断”；不能假装还有另一条结论。很短且影响题头理解时紧邻题头可见，下面不重复占块。 |
| 不同情况对应不同答案、处理或例外 | 显示逐项配对的条件与结果。不能仅显示候选结果名称或一列无对应关系的条件。 |
| 结论的实际结果较长，如排序、评价表、多个对象的结果 | 显示“具体结果”，完整保留顺序、项目和作者所给关系。即使没有分支也应可阅读。 |
| 规则给出可能结果或结果应有的内容，但尚未用于当前输入 | 按作者声明展示规则的结果含义或可能结果，不标成当前已经得出的现场结果。公式或开放生成规则不必枚举未来所有值。 |

区域存在与否由已明确保存的内容职责决定，不由 Reader 从自然语言猜测。明确“没有独立分支”、尚未补齐、读取失败、语义未支持是不同情况，不能都解释成“没有”。创作时需核对是否漏掉必要条件；必要条件缺失时不能把其当作完整成品。没有独立分支也不等于整个判断毫无限制。

### 12.3 一条分支及整组分支需要说明什么

每条分支最少具有两个有明确关系的内容：

1. **条件**：什么情况下采用它。涉及专门变量、术语、别的议题结果时，应能找到其含义和输入关系。
2. **对应结果或处理**：采用什么答案，或怎样继续形成答案。可以直接保存内容，也可明确引用同题结果、机制步骤或有声明的依赖，不能留下无目标的箭头。

整组分支还必须交代适用的处理关系：

- **同时满足多条怎么办**：可以并用，还是只取一条；若只取一条，取舍或优先关系是什么。不能以文件数组顺序、卡片排序或 Reader 猜测决定。
- **一条都不满足怎么办**：采用作者声明的默认处理，或明确本规则不提供答案；不要求凭空创造万能答案，也不能暗自沿用最后一条。
- **缺少判断条件所需的资料怎么办**：按作者声明补充资料、转交判断或暂不选择。资料不足不是条件为假，不能借此跳到默认结果。条件逻辑本身尚未执行时也不能显示已命中。

对于天然互斥或已说明穷尽的分支，可以保存这项明确声明及相关定义，不强迫重复编写不可能发生的故事。若作者尚未决定冲突时如何取舍，可以把“需要本人决定”作为真实的处理规则；不能伪造一个偏好。若缺口已经违背本题承诺提供的用途，应缩小用途或留在待完善创作中。

例外必须明确它改变哪条通常判断、在什么条件下改变、怎样改变。否定或限制主张的关键内容不能被当作次要备注藏到文件追溯里。

### 12.4 三种结果身份保持分开

- **结论的结果**：作者实际写定的答案，属于该资产内容。
- **规则的结果**：规则要求产生的答案含义、结构和已声明的可能情况；不是对用户当前输入已经完成的判断。
- **一次使用的结果**：将规则用于具体任务后产生的记录；只有实际发生且有相应记录才显示，不是打开文件自动生成的资产正文。

“条件与结果”区以保存的资产内容为准。作者的立场、偏好和经验不因缺少一次运行记录而被打成未完成；也不为每一题增加“尚未运行”的醒目说明。来源、运行日志和访问状态不能充当判断正文。

## 13. 一个完整议题的最小信息与按需信息

### 13.1 每题都要能明确取得的信息

这里规定的是语义上完整，不要求全部信息变成顶层独立字段或常驻屏幕卡片。

| 必要信息 | 要求 | 人类阅读位置 |
|---|---|---|
| 议题身份与完整问题 | 稳定 ID 供工具引用；唯一人类名称就是完整问题，没有另造的导航短名称。 | 左侧问题；技术 ID 不占正文。 |
| 三个分类 | 判断形态、回答类型、形成方式各单选已有一项，含义与正文相符。 | 题头三标签。 |
| 核心判断 | 作者明确写定的核心答案或判断原则；重要限定不可省掉。 | 右侧题头。 |
| 完整答案或完整办法 | 结论保留实际答案；规则保留从所需输入到答案的必要标准、过程或关系。核心句与展开共同形成一份判断。 | 题头、机制及实际需要的条件结果。 |
| 形成方式对应的必要机制 | 按已讨论的角色模板保存实际感受、经验、标准或关系；简单感受可以引用核心表达，不编造理由、不凑卡。 | 机制区域；重复的同一内容不复制成第二份主张。 |
| 判断主体与适用范围 | 说明这代表谁的判断，以及讨论什么对象、任务或情境。主体可以是个人、组织或明确声明的其他来源，无须公开真实姓名。 | 全资产一致的信息可以集中展示；本题差异、重要限制就近明确显示。 |
| 答案的含义与结构 | 明确最终回答什么；需要数值单位、排序方向、类别定义等才能理解时保留。机器类型如 text/list 继续服务交换，不能冒充三标签中的回答类型。 | 有助理解的说明呈现；技术编码不占常驻标签。 |

资产共同主体与范围可以在人类页面集中显示，以免每题重复。但**当前协议要求每题明确 subject 和 scope；父子议题不自动继承范围、边界、例外或误用声明**。本轮没有增加默认继承语义。未来若用共同声明引用减少重复，须建立明确可解析关系；不能因页面集中展示就删除每题所需表达。

### 13.2 有真实内容或理解需要时必须保留的信息

“按需”不是允许随意删掉已知内容，而是不强迫没有这种内容的议题造出来。

| 信息 | 什么时候必须有 | 位置与注意 |
|---|---|---|
| 条件、分支、具体结果 | 本题的答案随情况变化，或结果无法由核心句完整容纳。 | 条件结果区；保留适用的组合、冲突和缺资料处理。 |
| 边界、例外、误用提醒 | 已知限制影响理解或应用，或作者明确不允许某种推用。 | 本题就近可见；全资产共同边界在边界页。没有声明不解释成无限适用。 |
| 输入、参数和概念定义 | 规则依赖这些输入，或术语存在必须澄清的专门含义。 | 相关机制旁显示；单位、口径、时间、空缺等按实际需要定义。输入不要求创作时已取得所有未来数据。 |
| 与其他议题或材料的关系 | 本题使用别题结果、限定别题、反驳别题或共享前提。 | 内核给全局关系，本题给相关关系与准确入口。目录父子关系不能冒充逻辑依赖。 |
| 支持、反对、限定或校准理由 | 作者实际表达了这些理由，尤其会改变理解时。 | 按角色关联判断/机制/条件；理由不都等同于形成步骤，反对意见不改成支持。 |
| 解释性材料、示例与来源 | 本题需要某材料才能读懂或应用；或者作者选择提供公开来源和实例。 | 必要定义和内容随必需引用可取得；示例说明自身身份，不冒充实际运行。个人感受不强制学术来源。 |
| 局部署名、时间与演变状态 | 本题代表的主体、时间或修订情况与资产共同信息不同；本题明确撤回、替代或弃用。 | 必要状态明显可见，详细变更可在文件页追溯；不能让已撤回判断看似仍在正常采用。 |

对一个声明了依赖关系的判断，拿不到必要依赖时不能把剩余半句称为完整读到。是否允许自动远端获取、是否有读取授权是工具与访问合同的问题，Reader 不借链接绕过权限。这个要求不等于强制把所有私人创作材料、访谈、日志和源文档都塞进成品。

### 13.3 不要求每个议题重复保存或常驻展示的内容

- 整个资产的名称、创作背景、维护者、整体版本、许可、分享和保护状态、整体变更历史，在资产或文件层统一处理。某题的差异单独声明，不用重复粘贴全份元信息。
- 不强制每题有引用、反例、示例、数值权重、置信度、检验报告、运行结果；有实际必要内容时才按其角色保存。
- 创作提示词、工具日志、构建参数、哈希、SDK 版本等不成为议题正文。必要审阅追溯可在相应入口，但不能淹没核心内容。
- 不新增导航短标题、第二套长短结论、自动摘要、固定数量空组件、空分支或阅读全文跳转来弥补职责不清。

## 14. 与现有公共协议的对照及剩余工作

### 14.1 本轮核到的既有能力与边界

唯一公共语义源仍是本仓 specs/public-semantic-source.json；本节是对照分析，不是第二套 wire Schema。只读研究证明其中写了什么，不替代实际运行或交付验收。

| 现有定义 | 现有内容 | 与本轮定义的关系 |
|---|---|---|
| Judgment / Result / FormationRule / ResultContract | 问题、主体、范围、结论或规则及结果约定。 | 保留这些内容职责；补齐统一核心句、三个强制语义分类及唯一完整问题名称。当前仍存在 label/focus、可选 method 等旧结构。 |
| Condition / FormationRule.conditions | 有自然语言、结构化或外部解释声明；条件数组可以为空。 | 不等于每题已有条件—结果配对；也不要求每题有分支。条件声明不是 Reader 的执行许可。 |
| kdna.static-policy/1 | 明确条件对应候选结果、优先次序、兜底；按优先级只选一个候选。缺少前序条件判断会阻止后序选择和兜底。 | 这是一种已有且有界的分支合同，不能说从未定义，也不能扩称支持所有分支组合。 |
| MethodUse / MethodComponent / MethodBinding | 方法、组件、绑定；已有专门组件合同支持 taxonomy / candidate-set / discriminator-set 三类内容。 | 有组件基础不等于本轮 17 种方法的必要角色、内容及关系均已规范并实现。 |
| Reason / Material / SourceRef / SourceUse | 支持、反对、限定、校准理由；定义、前提、实例、附件及来源关系。 | 应保留其角色，不能全部摊成“判断机制”或删掉。公开来源不是所有议题的必填项。 |
| Relationship / Dependency / Cohesion / parent_ref | 议题关系、输入依赖、资产整体组织与目录层次。 | 内核需要这些共同关系；阅读单题仍须取得相关的必要依赖。目录层次不产生范围继承。 |
| Boundary / Exception / Misuse / Lifecycle | 适用限制、例外、误用及弃用/替代/撤回状态。 | 不应在简洁化时消失；不存在的声明也不能被 Reader 自动补造。 |

static-policy 的额外限制须原样保留：它只作用于规则；此版采用该模块时，原 formation_rule.conditions 必须显式为空，每项分支自带完整条件，不能擅自合并、搬移或覆盖原条件。它支持自然语言条件、明确优先方向及单一候选选择，Core/Read 不执行条件或选结果。需要多条并用、累积结果或其他组合的议题，不能硬套“只选一个”；现有普通文字可保存作者表达，但不据此声称已具有对应的共同结构化解释能力。

### 14.2 收口需要补的是共同语义与跨层一致性

1. 唯一问题名称、三维固定分类及必选规则、核心判断职责、方法角色映射进入共同合同；现有旧字段逐项给出承接或迁移关系，不只改 Reader 中文名称。
2. 对需要分支的内容明确条件与结果配对、组合及兜底语义；优先复用已存在的结果、条件和 static-policy 定义。超出其有界能力的形式明确表达及支持方式，不伪装已有实现。
3. 所有必要条件、范围、理由、依赖和定义按身份保留，并能跟随读取目标取得。作者没有提供的材料不能自动补成存在；作者明确没有的分支也不能强制生成。
4. 完整性检查有两层：工具确定检查分类合法、必需角色、引用、结果形状和分支配置；内容审阅核对是否回答了问题、是否遗漏限定或把一个方法步骤当总体判断。两者都不替作者裁定结论的对错。
5. 迁移后的旧内容必须逐项对应，公开 Read、Agent 与 Reader 取得同一含义；把字数、卡片折叠和分页当作呈现约束，不能让 UI 决定或删改资产语义。

### 14.3 后续验证应覆盖的区别（本轮未执行）

应包括：无分支的感受结论；无分支的顺序规则；单一适用条件；长排序结果；公式与开放结果；有明确优先级的分支；可同时成立并用的分支；无匹配；缺资料；共享定义和跨题依赖；反对理由；明确替代/撤回状态。相同内容要比较作者表达、公共读出、Agent 所读和 Reader 所见，不能只检查字段出现。

Reader 的直观检查仍是：左边问什么，题头回答什么，三个标签说明什么，机制怎样形成判断，条件改变什么结果，哪些范围与关系不可漏。检查应覆盖实际不同类型，不要求所有议题拥有同样长度、分支或组件数量。
