# Authoring workflow /2 adoption

This independent module is `kdna.authoring-workflow/2`, version `2.0.0`. The normative descriptor is the `authoring_workflow` object in the single public semantic source, exposed by Core's Node producer API `getAuthoringWorkflowContract()`. Its definition digest is SHA-256 of that descriptor's canonical JSON, excluding the returned digest field. This document explains adoption; it is not another rule registry or validator.

The prior `/1` descriptor had a named implementation scope. `/2` deliberately changes that contract shape: the common workflow rules no longer designate one exact Studio release as their sole consumer. A tool must explicitly adopt the exact id, version and definition digest, and separately bind its own implementation/package identity and complete dependency bytes. Wrong contracts, altered descriptors or mismatched implementation identities reject. No configurable compatibility registry, fallback to `/1`, or arbitrary implementation string is implied.

One or more genuine candidates may be proposed. Selection and final confirmation or rejection are distinct real responses in the declared role/channel; one candidate does not select or confirm itself. A revision invalidates earlier selections and previews. A restored draft has no restored live adoption authority. The current full preview, intent, question, source obligations and actual responses must bind the exported bytes and saved-byte check.

Concrete implementation evidence records the whole workflow descriptor, actual producer version, exact dependency graph, current content and role-bound response history. Static replay proves only its declared consistency boundary. A descriptor or serialized response does not create a live context, verified actor identity, content truth, read permission or action authorization.

The original `/1` contract and earlier creation.6/creation.7/grammar.2 implementation evidence remain frozen under their exact old packages. Changing a label, descriptor or producer field cannot upgrade that evidence. New `/2` consumers require their own actual package and behavior receipts, including wrong-contract, wrong-implementation, descriptor-tampering, historical-evidence relabeling, absent selection/final response and stale-preview counterexamples.

This module changes no Container/Payload/IR/Read/execution tuple, judgment schema or admission semantics, CS1/static-policy definition, or digest byte domain. The old/new structural classifier is expected to report `REQUIRES_NEW_COORDINATE` and exit nonzero; the required new coordinate is this authoring module. Independent review must verify the precise source difference and unchanged adjacent behaviors. New package versions, module coordinate, actual consumer acceptance and publication remain separate facts.
